# 記帳小幫手

手機優先的記帳 PWA。純前端（HTML/CSS/JS，無框架、無建置工具），資料存在瀏覽器的 IndexedDB，不需要帳號、不需要伺服器也能用。

想換手機不掉資料的話，另外有一個自己架的同步後端（`server/`），在「更多」頁登入就會自動同步；不登入的話一切照舊，完全離線。

## 本機執行

用任何靜態伺服器啟動這個資料夾即可，例如：

```
npx serve .
```

或

```
python -m http.server 8000
```

開啟後用手機瀏覽器（或桌機瀏覽器縮小視窗）打開該網址，選「加到主畫面」即可像 App 一樣使用，離線也能開啟。

## 功能

- 快速記帳，欄位順序是**日期 → 種類 → 評分 → 金額 → 備註**；日期在最上面一條，左右箭頭一天一天調（點日期本身會開系統日曆），記完馬上在同一頁看到月結算
- 分類管理，可自訂名稱、線條圖示與顏色（全 App 不使用 emoji）
- 消費明細列表，依月份/分類篩選
- 月結算：分類佔比圖、近 6 個月趨勢圖、預算與超支提醒（就在「記一筆」頁下半部）
- 美食評分：食物／飲料分類可以打 1–5 顆星，「評分」頁籤有排行、平均分與待評分清單
- 多人分帳：記帳時可標記「與人分帳」，分法有**平均／份數／自訂金額**三種（份數就是「一間雙人房兩個人住」那種 1:2，按比例分，餘數用最大餘額法補），只有你的份會計入月消費；「更多」頁籤裡的「分帳總覽」會算每個人欠你多少、你欠誰多少，可登記結清（純本機計算，不會跟對方的手機同步）
- 方案：一次出遊／一個計畫開一個方案，設定日期和同行的人，裡面有兩頁
  - 帳全部結清時會問要不要**把方案收起來**（封存）。收起來只是不顯示在列表上，資料一個都不動，在列表最下面「已收起來的方案」點開就找得到，隨時可以重新打開
  - 攜帶清單：加項目、勾選「準備好了」，可以指派誰帶什麼，也能給項目分類（內建生活／實習／電器／證件／藥品，選單最後一項「＋ 新增分類…」可以自己加），列表能切「依項目／依分類／依人」三種看法
  - 算帳：記下這趟每一筆花費（總金額、誰先付、誰要分、平均或自訂），自動算出每個人付了多少、該分多少，再給一份「最少轉幾次帳」的轉帳建議，按「登記結清」就能把帳沖掉
- **共享方案（選用，要登入同步）**：一個方案可以幾個人一起用，各自登入自己的帳號。發起人在方案頁按「共享」拿到邀請碼，對方在「方案」頁按「加入共享」輸入邀請碼，再選「我是名單上的哪一位」就進來了。之後這個方案的攜帶清單、花費、結清紀錄大家看到的是同一份，而且**每個人算出來的「我的份」是自己的那一份**（同一筆帳，我這邊顯示「別人要還我」，對方那邊就是「我要還別人」）。你其他的記帳不會被看到；發起人可以「解散共享」，成員可以「離開共享」
- 每筆花費可以夾一張**收據照片**（存進去前會壓到長邊 1400px 的 JPEG）
- 資料匯出／匯入（JSON 備份，含分類、支出、預算、同伴、結清紀錄、方案與攜帶清單）、匯出 CSV
- **雲端同步（選用）**：在「更多」頁填自己的伺服器網址登入之後，記帳資料會自動同步。離線照樣記帳，連上網再補傳；兩台裝置改到同一筆時，時間比較新的那份贏。收據照片不同步（見下）

## 幾個設計上的取捨

- **收據照片不進 JSON 備份。** 存在自己的 `receipts` store 裡（key 就是 expenseId），刻意跟 expenses 分開——不然每次列支出都會把照片一起讀進記憶體。不進備份是因為 `JSON.stringify` 碰到 Blob 會安靜地變成 `{}`，就算改成 base64，幾十張也會讓備份檔從幾十 KB 變成幾十 MB。「更多」頁在你有收據時會直接講這件事。
- **份數分帳只存份數，不存百分比。** 1:2 和 100:200 算出來的金額一樣，但份數是使用者的意圖，所以 `split.method = "shares"` 時會把 `weights` 一起存下來，回頭編輯才不會退化成一堆自訂金額。平均和自訂不用存——它們從 `shares` 的金額就還原得回來。

- **共享資料裡不可以出現 `me`。** 每台裝置的「我」都是同一個字串 `me`，直接同步過去就變成對方了。所以開始共享時會把這個方案裡所有指向「我」的地方（誰先付、誰分多少、誰要帶）換成一個真正的成員 id，名字放在方案的 `roster` 欄位跟著同步；解散共享時再換回 `me`。每台裝置只要記住「我在這個方案裡是哪一位」，其他畫面完全不用改——`tripMembers()` 回傳的 `meId` 就是那個人。
- **`expenses.amount` 是本機投影，不是共享內容。** 它存的是「我的份」，每個人的答案都不一樣，所以共享的花費拉下來時會照自己的身分從 `split` 重算一次（`shares.js` 的 `myShareOf`），寫回去走 `rawPut` 不重新排隊。共享的定案是 `split`，`amount` 只是為了讓月結算不用每次重算。
- **共享方案裡的成員是 `roster`，不是本機的同伴。** 同伴（`people`）永遠只屬於自己的帳號、不會共享出去——不然對方會拿到你整份通訊錄。發起人原本勾的同伴會在開始共享時複製成 roster 的一列，id 沿用，所以舊帳上的「小明」和加入之後的「小明」是同一個人，「分帳總覽」不會因此裂成兩筆。
- **分類會跟著共享的花費夾一份長相過去。** 分類是各自帳號的東西（不共享），對方沒有那個 id 的話整筆會變成「未分類」，所以推共享花費時順手夾上 `categoryMeta`，收到的人本機沒有就照著補一份。已經有同一個 id 就不覆蓋——本機自己改過的名字和顏色比較重要。
- **共享方案的成員名單走 API，不走同步。** 「誰在這個 share 裡、我是哪一位」是每輪同步跟伺服器問一次的（`GET /api/shares`），存在 `syncMeta` 裡給離線用。放進同步資料流的話，成員資格會被 last-write-wins 影響——兩個人同時加人，慢的那個會把快的蓋掉。
- **攜帶清單的分類不是一張表。** 項目上直接存分類的名字（`category`），選單的選項是「內建幾個 + 這台裝置自己加過的（localStorage）+ 所有項目用過的」合起來。開新 store 的話 `db.js` 的 `SYNCABLE_STORES` 和伺服器的 `COLLECTIONS` 都要跟著改，而分類就是一個字串，跟著項目同步本來就會過去。代價是「加了分類但還沒有任何項目用它」只留在這台裝置上。

- **配色只有「深夜」一套**，沒有淺色版可切。深底是為了讓分類自己的飽和色跳出來，所以 `:root` 直接就是深色值、`color-scheme: dark`（原生日期選擇器、下拉、捲軸才會跟著變深）。要加淺色版的話，`css/styles.css` 的 `:root` 是唯一要動的地方，但 `components.css` 裡幾個寫死的值（`--color-dim`、header/tabbar 的 rgba、modal 遮罩）也要一起換成變數。
- 分類選擇器是一排橫向捲動的圓形圖示，不是格子。分類再多也只佔一排高度，代價是一次只看得到 5 個。

- 方案裡的花費就是一般的支出記錄，只是多帶了 `tripId`；記進去的 `amount` 只放「我的份」，帳單總額放在 `split` 裡，所以月結算不會被別人的份灌水（我沒有分到的花費就是 $0）。
- 方案的「怎麼喬」是多人一起淨算的最少轉帳，可能把 A 欠 B 的錢直接轉給 C；「分帳總覽」則永遠是以你為中心的兩人帳。跟你有關的結清兩邊都會沖掉，但個別對象的金額可能長得不一樣。
- 舊版的「出門清單」在資料庫升到 v4 時會自動變成方案（id 不變，清單項目照樣掛著）。舊的 `packingLists` store 留著沒刪，當作備援。

- **同步的身分是 `uid`，不是 `id`。** 支出、結清、攜帶清單項目的主鍵是 IndexedDB 的自動編號，每台裝置編出來的號碼不一樣，拿它當身分兩邊會對不起來，所以 v6 幫這些 store 多加了一個 UUID 欄位 `uid`（含 `uid` 索引）。分類、同伴、方案、預算的主鍵本來就是全域唯一的字串，`uid` 就直接是 `id`。
- **寫入的鉤子放在 `db.js`，不是各個模組。** `put` / `add` / `remove` / `clearStore` 會蓋上 `updatedAt`、產生 `uid`、把這筆排進 `syncQueue`，而且「寫資料」和「排隊」在同一個 IndexedDB 交易裡——分開寫的話中間斷電就會有資料改了卻永遠不會上傳。從伺服器拉回來的東西走 `rawPut` / `rawAdd` / `rawRemove`，不重新排隊，不然會來回彈。
- **刪除要留墓碑。** `remove` 會先把 `uid` 讀出來才刪，然後排一筆 `deleted: true`。少了這一步，另一台離線的裝置下次同步就會把刪掉的資料救回來。
- **第一次登入某個帳號時「以雲端為準」。** 新手機一開 App 就會生出預設分類，`updatedAt` 是「現在」，比雲端那份新——照 last-write-wins 走的話，會反過來把雲端改過名字的分類蓋掉。所以第一輪同步是無條件拉、拉完才推，本機獨有的資料還是會上去。
- **收據照片不同步**，跟它不進 JSON 備份是同一個原因。換裝置的話收據不會跟著過去，「更多」頁在你有收據時會直接講這件事。

## 改東西的時候

**改完任何前端檔案，一定要推 `sw.js` 最上面的 `CACHE_VERSION`。** Service worker 對靜態檔是 cache-first，版本號沒變的話，已經裝在手機上的那份會一直吃舊的 CSS/JS——改了完全看不出來，也不會報錯。新增檔案的話也要一起加進 `PRECACHE_URLS`。

**新增會同步的 store 時，兩邊都要加：** `js/db.js` 的 `SYNCABLE_STORES`（順便決定 uid 是 `"id"` 還是 `"field"`）和 `server/src/config.js` 的 `COLLECTIONS`。伺服器只收白名單上的 collection，漏一邊的話推上去會被退 400。

**新的東西如果該跟著共享方案走，還要加 `server/src/config.js` 的 `SHARED_COLLECTIONS`**（值是「這筆屬於哪個方案」寫在 payload 的哪個欄位）。沒加的話那個 store 只會留在自己的帳號裡，共享的人看不到。

## 注意

共享方案是**互相信任**的功能：同一個方案裡的人可以改（也可以刪）這個方案裡的任何一筆資料，跟你自己改沒兩樣，也沒有「誰改的」紀錄。方案以外的東西彼此完全看不到。

沒有登入同步的話，資料只存在這台裝置的瀏覽器裡，清除瀏覽器資料或換裝置會遺失，請定期在「更多」頁籤匯出備份。登入同步之後資料會有一份在伺服器上，但**收據照片還是只存在這台手機**。
